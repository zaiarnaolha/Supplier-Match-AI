# Guideline — Supplier Match AI

## 1. Загальний принцип роботи

Перед виконанням будь-якої задачі:
1. Покажи короткий план дій.
2. Дочекайся підтвердження користувача.
3. Тільки після підтвердження починай реалізацію.

Не виходь за межі переданого макета та поставленої задачі.
Не додавай нові сторінки, секції, функції або контент без прямого запиту.

Основний принцип:
**не створюй дизайн з нуля, якщо його можна перенести з Figma.**

Figma Supplier Match AI є основним джерелом правди для:
- структури сторінки;
- контенту;
- компонентів;
- кольорів;
- типографіки;
- spacing;
- radius;
- responsive-рішень.

---

## 2. Контекст продукту

Supplier Match AI — B2B SaaS-сервіс для пошуку та порівняння постачальників.

Основна аудиторія:
підприємці-початківці та малі бізнеси, яким потрібно швидше знаходити релевантних постачальників та порівнювати доступні варіанти.

Основна цінність:
скоротити ручну роботу з пошуку, збору, структурування та порівняння інформації про постачальників.

Продукт допомагає користувачу прийняти рішення, але не приймає рішення замість нього.

---

## 3. Джерело дизайну

Використовуй переданий Figma-макет Supplier Match AI як основне джерело дизайну.

Якщо доступний Figma MCP — спочатку отримай структуру, стилі, variables та компоненти безпосередньо з Figma.

Не відтворюй дизайн "на око", якщо потрібне значення доступне у Figma.

У макеті підготовлені:
- Desktop EN;
- Desktop UA;
- Mobile EN;
- Mobile UA;
- Foundations;
- Components.

Основні секції лендингу:

1. Header
2. Hero
3. Product Intro
4. Features
5. How It Works
6. FAQ
7. Trust
8. CTA
9. Footer

Структура коду повинна відповідати цій структурі макета.

---

## 4. Design System

Використовуй тільки значення з design system у Figma.

### Variables

У макеті використовуються collections:

- Color
- Spacing
- Radius

Для кольорів використовуються primitive та semantic tokens.

У компонентах і секціях віддавай перевагу semantic tokens, а не прямим HEX-значенням.

Наприклад:

`semantic/action/primary`

має використовуватися замість прямого:

`#4F46E5`

Якщо технологія підтримує CSS Variables, мапи Figma variables на CSS custom properties.

Приклад:

`semantic/action/primary`
→ `--semantic-action-primary`

Не створюй нових кольорів, spacing або radius без необхідності.

Якщо потрібного значення немає в design system — повідом про це користувача і запитай, що використовувати.

Не підбирай значення на око.

---

## 5. Typography та Effects

Типографіку бери тільки з Typography Styles у Figma.

У макеті використовуються, зокрема:

- Display / H1
- Heading / H2
- Heading / H2 Compact
- Heading / H3
- Body / Regular
- Body / Small
- Label / Small
- Button / Medium
- Brand / Name

Основні гарнітури макета:
- Instrument Sans
- Inter

Не замінюй їх системними або дефолтними шрифтами, якщо оригінальні шрифти доступні.

Effects / shadows бери з Effect Styles макета.

Не додавай власні тіні, border radius або декоративні ефекти.

---

## 6. Компоненти

Компоненти Figma мапи на компоненти коду максимально близько до структури дизайн-системи.

У Supplier Match AI підготовлені:

- Button
- Feature Card
- Step Card
- FAQ Item
- Language Switcher
- Brand Logo

Не створюй окремий компонент для кожного варіанта одного компонента.

Наприклад:

Figma:

Button
- Primary
- Secondary
- Ghost
- Small
- Medium
- Large

Код:

`<Button variant="primary" size="medium" />`

а не:

`<PrimaryButton />`
`<SecondaryButton />`
`<LargeButton />`

Те саме правило застосовуй до інших компонентів із variants/states.

Повторюваний UI не дублюй у коді.

---

## 7. Структура коду

Рефактор роби по ходу реалізації.

Винось повторювані та самостійні UI-елементи в окремі компоненти.

Тримай файли невеликими.

Один файл — одна зрозуміла відповідальність.

Орієнтовна структура може бути:

components/
- Button
- FeatureCard
- StepCard
- FAQItem
- LanguageSwitcher
- BrandLogo

sections/
- Header
- Hero
- ProductIntro
- Features
- HowItWorks
- FAQ
- Trust
- CTA
- Footer

Не ускладнюй архітектуру без необхідності.

Якщо стек або структура існуючого проєкту вже визначені — дотримуйся їх замість створення нової архітектури.

---

## 8. Layout

За замовчуванням використовуй:

- Flexbox;
- CSS Grid.

Структура layout повинна відтворювати Auto Layout та композицію Figma.

Не перенось координати Figma як абсолютні `x/y` позиції.

Absolute positioning використовуй тільки для елементів, які справді накладаються один на одного або не можуть бути реалізовані нормальним document flow.

Не використовуй absolute positioning для побудови основної структури сторінки.

---

## 9. Responsive

Макет містить Desktop та Mobile версії.

Використовуй їх як джерело responsive-поведінки.

Не просто масштабовуй desktop.

Відтворюй структурні зміни, які показані у mobile-макеті:
- напрямок layout;
- ширину компонентів;
- відступи;
- stacking;
- навігацію;
- typography;
- поведінку секцій.

Між контрольними розмірами використовуй природну responsive-поведінку Flexbox/Grid.

Не допускай horizontal overflow.

---

## 10. Контент

Використовуй текст із переданого макета.

Не переписуй заголовки, CTA, FAQ або інший контент без прямого запиту.

Не додавай нові маркетингові твердження.

Для декоративних або демонстраційних даних використовуй тільки fake/demo data.

Не додавай:
- реальні персональні дані;
- API keys;
- access tokens;
- credentials;
- секрети.

---

## 11. Функціональність

Це статичний маркетинговий лендинг.

Не реалізовуй без прямого запиту:
- login;
- registration backend;
- authentication;
- database;
- API;
- user accounts;
- dashboard;
- supplier search backend.

CTA можуть бути представлені як відповідні UI actions без створення неіснуючої backend-логіки.

FAQ повинен підтримувати передбачені дизайном стани Closed / Open.

---

## 12. Порядок генерації

Працюй послідовно.

### Крок 1

Отримай:
- контекст продукту;
- користувача;
- Figma-макет;
- секцію або екран, який потрібно реалізувати.

### Крок 2

Прочитай Figma через доступний інструмент/MCP.

Перед написанням коду перевір:
- frame names;
- hierarchy;
- variables;
- styles;
- components;
- variants;
- desktop/mobile layouts.

### Крок 3

Зроби перший прогін максимально близько до Figma без самостійного редизайну.

### Крок 4

Далі працюй секція за секцією.

Один крок повинен вирішувати одну зрозумілу задачу.

Після кожної секції:
- винеси повторюваний UI у компоненти;
- перевір design tokens;
- перевір layout;
- звір результат із Figma.

### Крок 5

Після завершення всіх секцій зроби повний QA сторінки.

---

## 13. Перевірка після кожної генерації

Після кожного суттєвого кроку самостійно перевір результат і коротко повідом користувачу:

1. Чи головна дія секції/екрана присутня та працює.
2. Чи структура відповідає Figma.
3. Чи використані компоненти замість дублювання UI.
4. Чи кольори, typography, spacing і radius походять із design system.
5. Чи немає випадкових default styles інструмента.
6. Чи немає horizontal overflow.
7. Чи не додано функціональність або контент, яких немає в макеті.

Якщо є відхилення від Figma — явно вкажи їх.

---

## 14. Preview та Publish

Перед publish перевір preview.

Після publish повторно перевір:
- layout;
- fonts;
- responsive;
- assets;
- interactions.

Якщо publish ламає те, що працювало у preview, не накопичуй workaround поверх workaround.

Спочатку знайди причину.

Якщо проблема спричинена зайвою складністю реалізації — спростити код.

---

## 15. Repository

Якщо використовується Git repository:

не створюй нову структуру проєкту, поки не перевіриш існуючу.

Якщо після підключення repository проєкт не видно:
1. перевір, чи підключення завершилось;
2. перевір repository;
3. перевір branch;
4. перевір directory;
5. тільки після цього звертайся до користувача.

Не перезаписуй існуючу робочу конфігурацію без необхідності.

---

## 16. Заборонено

Без прямого запиту користувача не:

- редизайнити макет;
- додавати нові секції;
- змінювати тексти;
- вигадувати design tokens;
- використовувати випадкові HEX-кольори;
- використовувати випадкові spacing values;
- дублювати компоненти замість variants/props;
- будувати layout переважно через absolute positioning;
- додавати backend;
- додавати authentication;
- додавати реальні персональні дані;
- додавати API keys або tokens.

---

## 17. Фінальний чек-лист

Перед завершенням задачі перевір:

- [ ] Структура сторінки відповідає Figma.
- [ ] Усі основні секції реалізовані.
- [ ] Desktop відповідає desktop-макету.
- [ ] Mobile відповідає mobile-макету.
- [ ] Немає horizontal overflow.
- [ ] Використовуються design tokens.
- [ ] Немає необґрунтованих hardcoded кольорів.
- [ ] Typography відповідає Figma Styles.
- [ ] Повторюваний UI винесений у компоненти.
- [ ] Figma variants відображені через component props/states.
- [ ] CTA присутні.
- [ ] FAQ має потрібні стани.
- [ ] Не додано зайвих сторінок або функцій.
- [ ] Preview працює.
- [ ] Published version перевірена.
- [ ] Код достатньо простий для подальшої підтримки.

Після перевірки коротко повідом:
- що реалізовано;
- що перевірено;
- які відхилення від Figma залишилися, якщо вони є.
